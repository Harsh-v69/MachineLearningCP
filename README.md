# tape-graph: TAPE as an LLM-free path-finding algorithm

> Given an implicit state graph G, a random start s0 and a goal set, find a minimum-cost feasible path under
> budget B. Fold candidate paths into a graph, solve for the best constrained path, execute one step, and
> re-solve from the state the world actually returned.

TAPE (Jeong, Kim, Lee 2026) uses an LLM to propose plans, folds them into a graph, and picks a path with an ILP.
This project removes the LLM and asks what is left: a planning loop over a state graph. Two changes:

1. **No LLM.** Benchmarks have a fixed goal and a random start (River Crossing; Sokoban with 1, 2 and 3 boxes; a
   Boxoban-style 4-box imitation; Rubik's 2x2x2 and 3x3x3 in the half-turn metric), so state structuring and merging
   are exact and cannot be gotten wrong by a model.
2. **More than one solver.** BFS, A*, weighted A*, IDA* and the CP-SAT ILP all run on the same graph, each with
   its own graph constraints (dead-end pruning, `g+h <= B` cut, bounded explicit subgraph for the ILP, resource
   budgets).

ReAct and TAPE are *simulated* with the paper's noise model (`delta` planning error, `eta` execution noise), so
they are models of LLM behaviour, not real LLM runs. No language model was run anywhere in this repository.

## Benchmarks

Seven generated benchmarks, each with a random-start generator and a true optimal length `T*` for every instance
(verified by an exact distance table or by the A* oracle), plus a loader for user-supplied Boxoban files.

| benchmark | size | heuristic | `T*` targets | instances (`--n 5`) | observed `T*` |
|---|---|---|---|---|---|
| `river` | 8 missionaries, 8 cannibals, boat 4 | trip-count lower bound | 4, 6, 8, 10, 12, 14 | 30 | 4 to 14 |
| `sokoban` | 7x9, 1 box | sum of Manhattan distance of each box to the nearest goal | 6, 10, 14, 18, 22 | 25 | 5 to 23 |
| `sokoban2` | 7x9, 2 boxes | same | 6, 10, 14, 18, 22 | 25 | 5 to 23 |
| `sokoban3` | 8x10, 3 boxes | same | 10, 14, 18, 22, 26 | 25 | 9 to 27 |
| `boxoban` | 10x10, 4 boxes, generated locally | same | 8, 12, 16, 20 | 20 | 7 to 21 |
| `cube2` | Rubik's 2x2x2, 9 half-turn-metric moves, 3,674,160 states | max of two pattern databases (5,040 and 729 entries) | 3, 5, 7, 9, 11 | 25 | 3 to 11 |
| `cube3` | Rubik's 3x3x3, 18 half-turn-metric moves | corner pattern database, 88,179,840 int8 entries, chunked build cached under `.cache/` | 3, 5, 7, 9 | 20 | 3 to 9 |

The Sokoban family uses the same generator (reverse play from a solved layout, depth 60 to 600; Boxoban-style 30 to 150)
with static dead-cell pruning. `sokoban2` and `sokoban3` fill every bucket at `--n 5` (about 3 s and 25 s respectively, as
measured when they were added). The 3x3x3 state is a corner coordinate plus three
edge-quad coordinates; a full-state BFS on the move tables reproduces the known 1/18/243/3240/43239 half-turn-metric
counts, and a slow test (`--runslow`) checks the real pattern database against the known depth-5 count (574,908).
`cube3` `T*` targets stop at 9 because at `T* = 10` weighted A* hit the 500,000-node cap on 1 of 2 instances (comment in `benchmarks.py`). All cube3 runs use
`--max_nodes 100000` (see the machine note below).

## Using real Boxoban levels

The repo ships no real levels and downloads nothing. The built-in `boxoban` benchmark is a locally generated 10x10,
4-box imitation. To run on real levels, obtain a file yourself in DeepMind's Boxoban text format (for example one of
the `.txt` files of the public `google-deepmind/boxoban-levels` repository, cloned or downloaded by you) and point the
CLI at it:

```bash
python -m tapegraph.bench solvers     --bench boxoban_file --boxoban_file path/to/000.txt --n 20 --out boxoban_real
python -m tapegraph.bench agents      --bench boxoban_file --boxoban_file path/to/000.txt --n 20 --episodes 20 --no_ilp --out boxoban_real
python -m tapegraph.bench constrained --bench boxoban_file --boxoban_file path/to/000.txt --n 20 --out boxoban_real
```

`--bench boxoban_file` and `--boxoban_file PATH` must be given together, and the benchmark exists only then (it is not
part of `all`). Each level starts with a `; <index>` line followed by its grid (`#` wall, space floor, `.` goal, `$` box,
`@` player, `*` box on goal, `+` player on goal). The loader is strict: a level that is not rectangular, has no or
several players, a different number of boxes and goals, an unknown character, or is not enclosed by walls stops the run
with an error naming the level's index. With this benchmark `--n` is the maximum number of levels used (the first `n`
in the file) instead of instances per `T*` bucket, and `--seed` has no effect. `T*` is computed by the A* oracle (node
cap 300,000). A level the oracle cannot solve, or that is already solved (all boxes on goals, `T*` = 0), is not dropped: every CSV gets a `solver=skipped` (`method=skipped` for
agents) row for it with `T=-1` and the oracle's status (`no_path`, `node_limit` or `already_solved`); rows for loaded levels also carry
an `index` column (position in the file). A tiny hand-made 3-level sample in this format is in
`tests/data/boxoban_sample.txt`. **No results on real Boxoban levels are included in this repository**; every published
table uses only the generated benchmarks.

Notes: the validator checks rectangular rows, legal characters, one player, as many boxes as goals, and that the player
cannot reach the grid border. It does not require 10x10, does not accept `-` as a floor character, and does not check
that boxes are reachable: a level with an unreachable box simply comes back as a `skipped` row (`no_path` or
`node_limit`). Output files are named `<command>_boxoban_file.csv`, so two different level files written to the same
`--out` overwrite each other; use a separate `--out` per file.

## How the results were produced

Single machine, seed = CLI default (1). Defaults for everything not listed: budget `B = T* + 2`
(`--slack 2`), `--max_nodes 500000`, ILP `time_limit` 10 s per solve (the limit applies to the solver; graph construction and model building add to the wall-clock, so recorded `timeout` rows take 10 to 24 s), `--delta 0.16`, `--eta 0.04`, `--N 16`,
`--res_frac 0.9`. The solvers, agents and `frac` constrained runs used `--n 5` instances per `T*` target for every benchmark (the `bind` runs use other `--n`, see above; River 6 targets = 30 instances, Sokoban
25, Boxoban 20, Cube2 25, and the counts in the benchmark table for the newer ones). Instances are accepted within +-1 of the target and reported under their true `T*`, so
rows in the tables are keyed by actual `T*` and have 1 to 5 instances each.

Wall-clock of the original runs, from the run logs:

| benchmark | solvers | agents | constrained (`frac`) |
|---|---|---|---|
| river | `solvers --bench river --n 5` (4 s) | `agents --bench river --n 5 --episodes 100` (238 s) | `constrained --design frac --bench river --n 5` (4 s) |
| sokoban | `solvers --bench sokoban --n 5` (12 s) | `agents --bench sokoban --n 5 --episodes 100` (367 s) | `constrained --design frac --bench sokoban --n 5` (13 s) |
| boxoban | `solvers --bench boxoban --n 5` (140 s) | `agents --bench boxoban --n 5 --episodes 20 --no_ilp` (2267 s) | `constrained --design frac --bench boxoban --n 5` (136 s) |
| cube2 | `solvers --bench cube2 --n 5` (228 s) | `agents --bench cube2 --n 5 --episodes 30 --no_ilp` (812 s) | `constrained --design frac --bench cube2 --n 5` (171 s) |

**Machine contention.** The original solvers and `frac` constrained runs were done sequentially (about 710 s in
total), the `bind` runs one at a time, and the later solver and constrained runs (new benchmarks, the `c_slack` sweep)
also one at a time and not overlapped with development work, so those `seconds` columns are uncontended. The agents runs
are different. The original agents runs were **re-run after a seeding fix** (commit b7f6106: before it, every instance in a benchmark received the
same noise draws; now each instance gets its own seed `seed + 7919 * index`, shared by all methods of that instance so
the comparison stays paired; the first agents results were discarded) and ran as parallel processes (longest 2267 s). The
newer agents runs (sokoban2, sokoban3, the cube3 run, river and sokoban at 300 episodes) also ran in parallel with each other and
with development work, so **every agents `seconds` column is contended** and inflated by an unknown amount; a 10 s ILP limit
that was hit under contention could also have been met without it. Also, `react` and `tape` `seconds`
include Oracle distance computations (A*, 300k node cap, on off-path states; e.g. 14 to 17 s per episode on one
Boxoban `T*` 7 instance, against about 0.002 s for `ours_astar`), so they are not comparable to the `ours_*` times.
The cube3 runs were capped at `--max_nodes 100000` because of RAM on the development machine (the generic A* used
roughly 7 KB per expansion); the cube3 oracle that fixes `T*` and drives the simulated baselines has its own 300,000-node cap
that `--max_nodes` does not change. cube3 agents need about 2-3 GB of RAM per process (the oracle's fixed 300k-node cap is ~7 KB per expansion and ignores `--max_nodes`).

Deviations from the nominal loop above:

- **Fewer episodes for the expensive benchmarks.** Boxoban agents used `--episodes 20`, Cube2 and sokoban3 `--episodes 30`,
  sokoban2 100, and river and sokoban 300 in the superseding run (100 in `main`), instead of one common number. With 20 to 30 episodes a
  success rate has a standard error of roughly 0.05 to 0.09 per instance, and the Boxoban and Cube buckets have 1 to 5 instances each.
- **ILP disabled in the Boxoban, Cube2, sokoban3 and cube3 agents runs.** The Boxoban and Cube2 runs were started through a small uncommitted wrapper
  that set `ilp.ORTOOLS_AVAILABLE = False` before calling `bench.main()` (now the `--no_ilp` flag; see Run); sokoban3 and cube3 used `--no_ilp`. Consequences: (a) there are **no `ours_ilp` rows**
  for these benchmarks; (b) their `tape` rows used `ilp.graph_path_bfs` (a BFS shortest path on the

  100`, then `--episodes 30`) that were started and abandoned without writing a CSV (the first Cube2 one ran about
  28 min by log timestamps). The logs do not state the reason for abandoning them; the timeout and size numbers

**Does the ILP win anywhere?** Not in any regime tested here, with the thin-data caveats below. The regime where it might help, a resource budget that forces a longer path, was barely exercised by the `frac` design; the `bind` design exercises it, thinly on the multi-box Sokoban benchmarks and Boxoban (below).
- Unconstrained: the ILP is the slowest of the five solvers in every `(benchmark, T*)` bucket of the original four benchmarks except Cube2 `T*` 11 (34 to
  136 times slower than A* on River and Sokoban, bucket-level ratios). Its node count is below BFS in some Sokoban and Boxoban buckets, but
  ILP "nodes" is the size of the bounded subgraph it builds. The Cube2 `T*` 11 exception (ILP 3.3 s vs A* 4.4 s) is a
  bucket where it solved 0 of 5 and failed fast with `too_large`. Over all seven benchmarks: faster than A* on 0 of the 142 instances where both solved.
- Constrained, `frac` design, main table (`res_frac` 0.9): the ILP never solved more instances than A*, and was faster only in a row
  where it solved 0 of 5 (Cube2 `T*` 11). **But the resource budget never lengthened the optimal path in any solved
  instance:** all 30 instances A* solved (River 24, Cube2 6) have `cost == T*`, and the 24 the ILP solved (all River) too.
  In the supplementary runs exactly 3 solved instance-runs were forced to a longer path (Sokoban `T*` 17 at 0.95, and
  `T*` 17 and `T*` 21 at 0.97, cost `T*` + 2 each; the two `T*` 17 runs are the same instance, so 2 distinct instances),
  and the ILP matched A* on all of them. Across the runs with `res_frac` below 1 (190 instance-runs), 156 were infeasible at the resource budget and 3 of the 33 solved A* rows had cost above `T*`.
  So for the `frac` design, the case a resource-constrained ILP is meant for (a
  budget that forces a trade-off against length) was effectively not exercised; that statement is about this design
  and its original resources only. The `bind` design below does exercise it (in its first, `c_slack` 4 run on four benchmarks: 131 A* rows and 110 ILP rows with the
  optimum strictly longer than `T*`), and there the ILP again matched A* where it solved and was slower, except on rows
  where it failed fast.
- Why Sokoban and Boxoban are infeasible below the optimum's resource (`frac` design, original resources): the resource is steps plus 2 per push (a push
  costs 3, a walking move 1). With length slack 2, a path can only use fewer resource units than the length-optimal
  path by using fewer pushes (each saved push saves 2 units; extra walking only adds), and `floor(X * resource of the
  optimum)` for X below 1 already needs at least one unit saved. A path with fewer pushes than the length-optimal one
  and at most 2 extra moves almost never exists, which matches the data (69 of 69 skipped rows in the main run are
  `infeasible` for A*; River and Cube2 resources are not tied to pushes and are infeasible only on the shorter buckets).
  I checked this structurally (the argument above) and by A* and the ILP agreeing on 8 spot-checked instances, not by
  enumerating push counts.
- The ILP's result on skipped rows was not stored in the published CSVs (A* alone decided `infeasible`). The current code
  records it as `ilp_status` on every skipped-infeasible row and `report` counts the rows where `ilp_status` is `ok` (a
  disagreement, expected 0); the published CSVs have none recorded (`0 of 69` in `docs/results.md`).
- Fairness caveat in both directions: the ILP's subgraph is the `{g + h <= T* + slack}` ball, which is larger than the
  `f <= T*` region A* expands (the spec's "same subgraph A* would expand" is only approximately true); its Python graph
  build counts toward its time; and CP-SAT runs with 8 workers against single-threaded A*.

### Constrained experiment, redesigned so the budget binds

**Why.** The `frac` design above never forced a longer path in the main table (and in only 3 supplementary instance-runs).
The likely cause is that its resources (steps plus 2 per push, passengers carried, quarter-turn 1 / half-turn 2) rarely
trade off against length: the probe below supports this empirically (0 of 30 River, 0 of 8 Cube2, 2 of 25 Sokoban and 0 of
3 Boxoban instances had a cheaper longer path), and for Sokoban and Boxoban the structural argument given under the ILP
verdict points the same way. I have not proven it in general. The redesign makes the resource constraint cut off every
length-optimal path while still leaving a feasible, longer one.

**Probe: do the resources trade off against length at all?** For each instance: does a path of length <= `T*` + slack
exist with strictly less resource than every length-`T*` path? Counts are instances with a trade-off / instances in the
set. The probe ran slack 2, 4 and 8 for River and Sokoban but only 2 and 4 for Cube2 and Boxoban; on the benchmarks and
resources where more than one slack was run the counts were identical across slacks, i.e. where a trade-off exists it
already existed at slack 2.

|---|---|---|
| River (30) | passengers carried (original) | 0 / 30 |
| River | missionaries x 3 | 0 / 30 |
| River | passengers squared | 7 / 30 |
| Cube2 (8; `T*` in {5, 7, 8}) | half-turn 2 / quarter-turn 1 (original) | 0 / 8 |
| Cube2 | quarter-turns only | 1 / 8 |
| Cube2 | half-turns only | 7 / 8 |
| Sokoban (25) | push 3 / move 1 (original) | 2 / 25 |
| Sokoban | pushes only | 2 / 25 |

| Boxoban | pushes only | 0 / 3 |

{5, 7, 8}, `n` = 3 for Boxoban filtered to `T*` in {8, 12, 16}. The probe's A* node caps were 300k (River, Sokoban) and
200k (Cube2, Boxoban), against 500k in the actual runs; an instance where A* hit its cap is not counted. The run's output
was not saved, so the table is not reproducible from stored data; the script is committed and should regenerate it, but I

**Design** (`constrained --design bind --c_slack C`; code: `bench.min_resource`, `bench.bind_budgets`,
`bench._constrained_bind`). For each instance, with `T*` the optimal length:
- `r_opt` = the minimum resource among paths of length <= `T*`; `r_min` = the minimum resource among paths of length
  <= `B = T* + c_slack` (default `c_slack` 4; the sweep below also ran 2 and 8). Both come from bisection over A* calls with a resource budget, so the
  bisection runs only A*.
- If `r_min >= r_opt` the instance is skipped with status `no_tradeoff` (a `solver=skipped` row).
- Otherwise there are two levels. `bind`: `R = r_opt - 1`, so every length-`T*` path violates the budget and the
  optimum is strictly longer than `T*`. `tight`: `R = r_min`, the hardest feasible budget. `tight` is run only when
  `r_min < r_opt - 1`; otherwise `bind` already equals `r_min` (this is the case for 7 of the 18 Cube2 trade-off
  instances).
- A* and the CP-SAT ILP both run at `(B, R)` with the same `--max_nodes`. `forced_longer` = 1 when the returned cost is
  above `T*`.

**Resources used** (`res_bind`, applied through a `ResView` wrapper; the original `res` is unchanged and still used by
the `frac` design): the Sokoban family and Boxoban count **pushes only** (walking is free); River counts **passengers squared**
(crowded boats cost more); the cubes count **half-turns only** (quarter-turns are free). These were chosen *because* they
create trade-offs (see the probe; the probe covered the four original benchmarks, the same resource definitions are applied to the newer ones). So this experiment tests solver behaviour under a binding resource budget; it says
nothing about which resource a real application would care about.

**Findings.**
- The constrained regime is exercised by the `bind` design. On River (43 of 120 instances have a trade-off, 86 rows) and Cube2 (18 of 20, 29
  rows) every solved row has a strictly longer optimum, as the construction guarantees; the size of the increase (above) is the
  informative part. On Sokoban (7 of 90 instances), sokoban2 (3 to 6 of 100), sokoban3 (4 of 50) and Boxoban
  (1 of 40) trade-offs are rare under this resource, so those rows are thin. (The statement "barely exercised" earlier in this README applies only to the `frac` design.)
- The ILP still wins nowhere that was measured. In the first `c_slack` 4 run, where both solved (110 pairs) it matched A* on cost every time and was 49x to 228x slower per
  benchmark (ratio of mean seconds on rows where both solved; Cube2's 228x rests on 8 rows). On Cube2 it solved only 8 of 29 rows (6 of 18 instances) and failed on every row at `T*` >= 7. The only rows with
  the ILP faster in that run are the Cube2 `T*` 11 failures.
- This is evidence about these seven benchmarks, these resources, `c_slack` 2, 4 and 8 (not every value on every benchmark), a 10 s ILP limit and the node caps used. It does not show that the
  ILP cannot win elsewhere (for example in a different formulation, with other objectives such as TAPE's node scores, or on much larger graphs).

**Caveats for this experiment.**
1. A* success at `tight` is partly tautological. The `tight` budget is `R = r_min`, and `min_resource` already ran A* at
   exactly `(B, r_min)` during bisection and got `ok`, so the A* call at `tight` repeats an answer already obtained (the same
   holds for `bind` on the 7 Cube2 instances where `r_min = r_opt - 1`). A* `ok` here must not be read as a headline solve
   rate; the informative quantity is the ILP's behaviour given that A* is feasible. Instances where A* hit `node_limit`
   during the bisection are skipped and would show in the failure breakdown, which biases the sample toward instances A*
   can handle. None occurred in the first run (all 201 skips are `no_tradeoff`); the cube3 run has one.
2. Small, skewed samples. Per-`T*` counts are listed above: River's trade-off instances sit at `T*` 4, 6, 10, 12 only,
   Sokoban has 7 instances over six `T*` values, Boxoban has one instance, and Cube2 has 18 trade-off instances (11 of them with a `tight` level).
   The unequal counts come from where trade-offs happen to exist, not from design.
3. Fairness asymmetries. The ILP's `max_nodes` counts states in the whole `g + h <= B` ball (no resource pruning; it grows
   with `c_slack`), while A* counts expansions after resource pruning and dominance. The ILP has a 10 s solver limit, which A*
   lacks. CP-SAT uses 8 workers against single-threaded A*. The bisection that picks `R` runs only A*. The sweep shows the Cube2 ILP failure
   rate rising with `c_slack`, and the data separate the two effects at the `bind` level: `R` and the optimum are fixed (A* mean nodes, e.g. cube2 41,166.6, are
   identical at every `c_slack`) while the ILP's mean nodes grow with the ball, so the sweep measures the edge-flow ILP's sensitivity to a slack length budget, not a harder trade-off.
   The sweep runs at the same `--n` as the `c_slack` 4 runs (a deliberate choice, so the instances pair across runs; a larger `--n` for the sweep was not run).
4. `agrees_with_astar` is 0 both when the ILP failed and when the costs differ. Every row where both solvers returned
   a path is an ok-vs-ok pair, and the costs are equal on all of them (110 in the first run, 362 over all runs), so the zeros are ILP failures, not disagreements.
5. The `res_bind` resources (pushes only, passengers squared, half-turns only) are unusual
   resources chosen for having trade-offs (see the probe), not a realistic cost model.
6. The skipped rows record only A*'s bisection verdict (`no_tradeoff`); the ILP was not run on them.

## Caveats

- ReAct and TAPE are simulated with the paper's noise model, not real LLMs.
- The constrained ILP-vs-A* results come from two designs with different resources: `frac` (original resources, the budget rarely binds) and `bind` (resources chosen to create trade-offs; thin on the multi-box Sokoban benchmarks and Boxoban). See the caveats under "Constrained experiment, redesigned so the budget binds".
- Sokoban-family instances are rejection-sampled from long reverse random walks and reported by their true `T*`. Instances exist only where the oracle (an exact table, or A* with a 300,000-node cap) found `T*`, so the samples exclude instances A*-based search could not solve.
- TAPE-sim minimises path length in the folded graph, not TAPE's node-score objective.
- The ILP is an edge-flow formulation, not time-expanded.
- Cost means in the tables are over solved instances only.
- Buckets have 1 to 5 instances (and 20 to 300 episodes each), so success-rate differences of a few points are within
  noise at the bucket level; the pooled Wilson intervals assume independent episodes and are optimistic, the paired bootstrap over instances is the honest comparison.
- Agents `seconds` are contended (see "Machine contention" above). Several agents runs have the ILP disabled (boxoban, cube2, sokoban3, cube3).
- `Replan` still plays the first legal action when its solver returns a non-ok status (timeout, `too_large`,
  `node_limit`, or a legitimate `no_path`, e.g. when the remaining budget is exhausted off the plan), but the fallback is
  counted: `solver_fail` is the episodes' mean number of solves whose status was not ok, written to the agents CSV and
  shown in the agents table of `report`. The oldest published CSVs in `docs/data` predate the column; the earlier reading that
  `ours_ilp` is unaffected on River and Sokoban (the ILP never failed there in the solvers table) rests on
  the solvers table, not on a recorded count for those runs.
- `TapeSim` re-plans only when the state deviates from its plan (per our spec), whereas TAPE-main's
  `OursGraphILPPolicy` re-folds and re-solves at every step, so `solves` and `seconds` are not directly comparable
  with the paper.
- `TapeSim` calls `solve_graph` without a length budget, whereas TAPE-main passes `budget=budget_remaining`.
- No result on real Boxoban levels exists; no real language model was run.
